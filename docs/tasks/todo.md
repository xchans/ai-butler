# 할 일: request-ledger

계획은 [plan.md](plan.md), 기준은 [docs/spec/SPEC-request-ledger.md](../spec/SPEC-request-ledger.md)다. S 번호는 스펙의 완료 조건이다. 모든 작업은 끝날 때 `npm run check`를 통과해야 한다. 파일은 저장소 루트 기준으로 적고, `ledger/`는 `src/request-ledger/`를 줄인 것이다.

조회 함수는 한 번에 만들지 않는다. 작업 5에서 `getRequest`의 틀을 만들고, 그 뒤의 작업은 자기가 더한 것을 `getRequest`(와 필요하면 `listRequests`)에 함께 더해 그 작업의 테스트에서 조회로 확인한다.

## 2단계: 요청, 기록, 작업

1단계 리뷰에서 넘어온 일: `ledger/concurrency.test.ts`의 "다른 프로세스가 쓰기 잠금을 잡고 있으면 기다렸다가 쓴다" 테스트가 300ms 이상 기다렸는지를 시간으로 판정한다. 느린 환경에서 정상 쓰기를 실패시킬 수 있으므로, 작업 4를 시작할 때 잠금을 쥔 쪽이 상대의 조회 완료 신호를 받을 때까지 잠금을 유지하도록 바꾸고 시간은 진단에만 쓴다.

- [ ] **작업 4: 요청과 값**
  - 설명: `createRequest`, `updateRequest`, `setPriority`를 만든다. 값(제목, 요청자, 약속한 결과, 기한, 긴급도, 중요도)마다 정한 주체와 사용자 지정을 함께 저장한다.
  - 완료 조건:
    - 사용자 지정이 걸린 긴급도, 중요도, 요청자는 비서가 바꿀 수 없고, 풀면 바꿀 수 있다. 여러 값을 한 번에 쓸 때 하나라도 어긋나면 전체가 거부되고 오류에 그 값이 나온다 (S2).
    - 제목 없이 등록하면 거부된다. 미정으로 등록한 요청은 사용자나 비서가 풀 수 있고 다시 붙일 수 없다 (S15의 목록을 뺀 부분).
    - 값, 정한 주체, 사용자 지정이 모두 그대로인 쓰기는 이력을 남기지 않고, 사용자 지정만 풀어도 이력이 남는다 (S27).
  - 확인: `node --test "src/request-ledger/request.test.ts"`
  - 의존: 작업 2
  - 파일: `ledger/request.ts`, `ledger/value.ts`, `ledger/types.ts`, `ledger/migrations.ts`
  - 크기: M

- [ ] **작업 5: 요청 조회의 틀**
  - 설명: `getRequest`가 요청의 값과 변경 이력을 돌려준다. 값마다 정한 주체, 사용자 지정, 걸린 시각이 나온다. 뒤의 작업이 여기에 자기 것을 더한다.
  - 완료 조건:
    - 요청 조회에 값과 정한 주체, 사용자 지정이 걸려 있는지와 걸린 시각이 나온다 (S2의 조회 부분).
    - 비서가 정한 값을 사용자가 고치면 두 값이 변경 이력 한 건에 함께 나온다 (S27).
  - 확인: `node --test "src/request-ledger/get-request.test.ts"`
  - 의존: 작업 4
  - 파일: `ledger/get-request.ts`, `ledger/index.ts`

- [ ] **작업 6: 주체, 기록, 판본, 연결**
  - 설명: 주체의 형태와 같은 주체인지 가리는 규칙을 만들고, `addRevision`과 `linkRecord`를 만든다. 직접 맡긴 말을 사용자 채널의 기록으로 저장한다.
  - 완료 조건:
    - 원본 시각이 같은 판본은 하나이고 본문이 다르면 거부된다. 요청 조회에 연결된 기록의 판본들이 본문과 함께 나온다 (S10의 완료 근거를 뺀 부분).
    - 직접 맡긴 요청을 등록하면 접수 원본이 본문, 출처 `conversation`, 작성자, 말한 시각과 함께 주소 없이 조회되고, 같은 id로 다시 접수해도 기록은 하나다. 제목은 사용자 지정이 없고 요청자와 명시한 기한은 사용자 지정이 걸려 나온다. 이 기록을 다른 역할로 연결하거나 값 변경의 근거로 달면 거부된다 (S31의 닫힘, 보류 풀기, 다시 열기를 뺀 부분).
    - 식별자가 있는 주체와 이름만 같은 주체는 다른 주체다.
  - 확인: `node --test "src/request-ledger/record.test.ts" "src/request-ledger/party.test.ts"`
  - 의존: 작업 5
  - 파일: `ledger/party.ts`, `ledger/record.ts`, `ledger/link.ts`, `ledger/evidence.ts`, `ledger/migrations.ts`
  - 크기: M

- [ ] **작업 7: 작업, 선후 관계, 완료 표시**
  - 설명: `addTask`, `updateTask`, `completeTask`, `cancelTask`를 만든다. 선후 관계와 완료, 취소, 되돌리기를 다룬다.
  - 완료 조건:
    - 비서는 근거 없이 완료로 쓸 수 없고, 사용자가 표시한 완료를 되돌릴 수 없다. 두 완료가 조회에서 구분되고, 근거로 단 판본은 새 판본이 들어와도 바뀌지 않는다 (S5, S10).
    - 완료나 취소인 작업은 `updateTask`로 할 일, 진행 중, 대기로만 되돌릴 수 있고, 비서는 자기가 쓴 것만 그 뒤의 판본으로 되돌린다. 사용자가 취소한 작업은 비서가 되돌릴 수 없다 (S5).
    - 자기에게 돌아오는 선후 관계와 대기 대상 없는 대기는 거부된다 (S12, S13의 쓰기 부분).
  - 확인: `node --test "src/request-ledger/task.test.ts"`
  - 의존: 작업 6
  - 파일: `ledger/task.ts`, `ledger/dependency.ts`, `ledger/get-request.ts`, `ledger/migrations.ts`
  - 크기: M

- [ ] **작업 8: 확인할 사항**
  - 설명: `raiseOpenItem`과 `resolveOpenItem`을 만든다. 답하면서 값을 바꾸는 쓰기를 한 트랜잭션으로 묶는다.
  - 완료 조건:
    - 확인할 사항은 비서만 남기고 사용자만 답한다. 이미 푼 것에 다시 답하면 거부된다 (S39의 쓰기 부분).
    - 답하면서 값을 바꾸면 함께 저장되고 이력에 답이 근거로 남는다. 값 변경이 거부되면 답도 저장되지 않는다. 비서가 사용자 확인이나 답을 근거로 달면 거부된다 (S24의 닫힘을 뺀 부분).
    - 비서가 남긴 어긋남이 요청 조회에 나온다 (S5).
  - 확인: `node --test "src/request-ledger/open-item.test.ts"`
  - 의존: 작업 7
  - 파일: `ledger/open-item.ts`, `ledger/evidence.ts`, `ledger/get-request.ts`, `ledger/migrations.ts`

- [ ] **작업 9: 사실 정정과 나중 판본**
  - 설명: 사용자가 바로잡은 값을 비서가 바꾸는 조건을 만든다. 근거의 시각을 비교하는 함수와 변경 이력의 순번을 비교하는 함수를 한 곳에 둔다.
  - 완료 조건:
    - 사용자가 바로잡은 작업의 상태는 정정 뒤의 판본이 있어야 바뀌고, 늦게 도착한 앞선 판본으로 값이 되돌아가지 않는다. 사용자가 완료를 되돌린 작업을 비서가 예전 판본으로 다시 완료로 쓰면 거부된다 (S7, S9, S37의 판본 부분).
    - 사용자 지정이 걸린 약속한 결과와 기한은 나중 판본으로만 바뀌고 사용자 지정은 남는다 (S8).
    - 사용자 지정이 걸린 제목은 그 뒤에 기록이나 작업이 더해졌을 때만 비서가 바꿀 수 있고, 시각이 같아도 순번으로 가린다 (S32의 합치기와 옮기기를 뺀 부분).

## 3단계: 보류, 상태, 차례

- [ ] **작업 11: 보류**
  - 설명: `placeHold`와 `releaseHold`를 만든다. 보류를 하나씩 따로 저장한다.
  - 완료 조건:
    - 비서는 보류를 걸 수 없고, 재개 조건이 있는 보류만 건 시각 뒤의 판본으로 풀 수 있다. 직접 맡긴 말은 보류를 푸는 근거로 달 수 없다 (S3의 보류 부분, S4, S31).
    - 보류가 하나라도 남으면 보류로 조회되고, 요청의 보류를 작업 하나에서만 풀 수 없다. 요청 조회에 보류마다 식별자, 대상, 재개 조건, 건 시각이 나온다 (S4).
    - 한 프로세스가 보류하는 동안 다른 프로세스가 상태를 써도 보류가 유지된다 (S28 뒷부분).
  - 확인: `node --test "src/request-ledger/hold.test.ts"`
  - 의존: 작업 9
  - 파일: `ledger/hold.ts`, `ledger/get-request.ts`, `ledger/migrations.ts`
  - 크기: S

- [ ] **작업 12: 요청의 상태, 표시와 차례 계산, 목록 조회**
  - 설명: 접수와 진행 중을 작업에서 계산하고, 작업의 표시와 차례, 요청의 차례를 한 함수로 계산한다. `listRequests`를 만든다.
  - 완료 조건:
    - 표시 표의 줄마다 표시와 차례가 표대로 나오고, 두 줄에 해당하면 위의 줄이 나온다 (S13의 끝내기로 정한 요청을 뺀 부분).
    - 작업이 없거나 할 일과 취소만 있으면 접수, 진행 중·대기·완료인 작업이 있으면 진행 중이다. 끝나지 않은 작업이 없으면 다음 작업 미정이다. 미정인 요청과 진척이 목록에 나온다 (S14의 끝내기로 정한 요청을 뺀 부분, S15, S41).
    - 풀리지 않은 질문이나 승인이 있으면 요청의 차례에 사용자가 들어가고, 하나만 풀면 남으며, 미확인과 어긋남만으로는 들어가지 않는다 (S12, S39).
  - 확인: `node --test "src/request-ledger/display.test.ts" "src/request-ledger/list.test.ts"`
  - 의존: 작업 11
  - 파일: `ledger/display.ts`, `ledger/status.ts`, `ledger/list.ts`, `ledger/get-request.ts`
  - 크기: M

- [ ] **작업 13: 사용자가 정한 차례와 목록 순서**
  - 설명: `setTurn`, `clearTurn`, `setOrder`를 만들고, 목록을 처리 순서와 긴급도, 중요도, 기한, 접수 시각으로 정렬한다.
  - 완료 조건:
    - 사용자가 정한 차례는 담당과 상태를 바꾸지 않는다. 사용자가 `clearTurn`으로 지우면 계산한 차례로 돌아가고, 차례를 정한 시각 뒤의 판본으로 상태가 바뀌거나 작업이 끝나도 풀린다 (S11).
    - 비서는 처리 순서와 차례를 쓸 수 없다 (S3의 처리 순서와 차례 부분).

  - 완료 조건:
    - 방향 변경은 사용자만 주고 대상, 창구, 시각, 적용 범위와 함께 조회된다. 작업 하나에 준 방향 변경은 다른 작업의 배정에 전달할 것으로 나오지 않는다 (S40).
    - 보고에서 나온 확인할 사항의 답은 그 배정에, 끝났으면 같은 팀원과 같은 범위로 이어받은 진행 중인 배정에 전달할 것으로 나온다. 두 번 이어받아도 그렇고, 이어받은 관계 안에서 한 번 전달했으면 다시 나오지 않는다. 전달할 배정이 없으면 요청 조회에 전달하지 않은 답으로 나온다 (S40).
    - 방향 변경은 그때 있던 진행 중인 배정마다 전달할 것으로 나오고 배정마다 따로 센다. 보고를 가리키는 확인할 사항은 그 배정의 작업에만 달 수 있다 (S40).
