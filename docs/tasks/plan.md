# 구현 계획: request-ledger

기준 스펙: [docs/spec/SPEC-request-ledger.md](../spec/SPEC-request-ledger.md), [docs/spec/SPEC.md](../spec/SPEC.md)

## 개요

업무 원장을 만든다. 요청, 작업, 근거 기록과 판본을 SQLite에 저장하고, 사용자의 지시를 비서가 덮어쓰지 못하게 쓰기를 검사하며, 요청의 상태와 차례, 표시를 계산해 돌려준다. 여기에 맡긴 범위와 팀원 배정, 지시와 보고, 비서의 확인 내용을 더해 첫 버전의 실행 조율이 쓸 기록을 갖춘다. 작업 27개를 일곱 단계로 나눈다. 작업의 상세는 [todo.md](todo.md)에 있다.

## 설계 결정

- **상태 테이블과 변경 이력을 함께 쓴다.** 현재 값은 테이블에, 바뀐 내역은 덧붙이기만 하는 변경 이력 테이블에 한 트랜잭션으로 저장한다. 조회가 단순하고 스펙의 이력 조건을 그대로 확인할 수 있다.
- **모든 쓰기는 `BEGIN IMMEDIATE` 트랜잭션 안에서 규칙을 검사한다.** 다른 프로세스가 사이에 끼어들어 사용자의 지시가 깨지는 일을 막는다.
- **스키마는 마이그레이션 목록으로만 만든다.** 작업마다 필요한 테이블을 마이그레이션으로 더한다. 첫 작업부터 버전을 올리는 경로를 쓰게 된다.
- **접수와 진행 중, 차례, 표시, 이어 갈 수 없는 배정은 저장하지 않고 한 곳에서 계산한다.** 닫혔는지와 닫힌 이유, 끝내기로 한 사유는 저장한다. 목록 조회, 요청 조회, 배정 조회가 같은 계산 함수를 쓴다.
- **조회는 쓰기와 함께 자란다.** `getRequest`의 틀을 2단계에서 만들고, 뒤의 작업은 자기가 더한 것을 조회에도 더해 그 작업의 테스트에서 조회로 확인한다. 마지막 작업에 조회를 몰아 두지 않는다.
- **단계 확인은 그 단계에서 만들 수 있는 것만 본다.** 완료 조건 하나가 여러 단계에 걸치면, 단계 확인에 어느 부분을 뒤 단계에서 마저 확인하는지 적는다.
- **"앞뒤"를 따지는 규칙은 두 가지 기준만 쓴다.** 근거의 시각(판본은 원본 시각, 보고 근거는 보고를 받은 시각)과 변경 이력의 순번이다. 두 비교를 각각 함수 하나로 두고 모든 규칙이 그것을 쓴다.
- **쓰기 함수는 값의 종류별 파일로 나눈다.** `src/request-ledger/` 안에 요청, 작업, 기록, 보류, 닫기, 묶음, 맡긴 일, 조회를 따로 두고 `index.ts`만 밖으로 내보낸다.
- **스펙의 표를 테스트 표로 옮긴다.** 쓰기 계약, 닫기의 쓰기 여섯, 표시 일곱 줄, 이어 갈 수 없는 사유 다섯은 표의 행마다 테스트 사례를 둔다.
- **위험한 것부터 확인한다.** 여러 프로세스의 동시 쓰기는 Node 내장 SQLite에서 실제로 되는지가 관건이어서 첫 단계에 둔다.

## 순서

일곱 단계를 순서대로 한다. 5단계의 합치기는 4단계의 닫기에, 6단계는 4단계와 5단계에 의존하므로 단계를 나란히 진행하지 않는다. 한 단계 안에서도 작업은 번호 순서대로 한다.

1~5단계를 먼저 구현하고 VOC 시나리오로 닫는다. 6단계와 7단계는 `coordination`과 `agent-runtime` 스펙을 쓴 뒤에 구현한다. 6단계의 저장은 두 스펙을 쓰면서 바뀔 가능성이 높기 때문이다. 두 스펙을 쓰는 일은 1~5단계의 구현과 나란히 할 수 있다.

## 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| Node 내장 SQLite가 여러 프로세스의 동시 쓰기에서 잠금 오류를 낸다 | 높음 | 작업 3에서 먼저 확인한다. 안 되면 재시도나 쓰기를 한 프로세스로 모으는 방식을 스펙에 먼저 적고 묻는다 |
| 구현하다 스펙의 규칙이 서로 부딪히는 곳을 찾는다 | 높음 | 추측으로 정하지 않고 스펙을 먼저 고쳐 사용자에게 묻는다. 6단계의 규칙은 리뷰에서 지적이 많았던 부분이라 단계 확인에서 다시 돌아본다 |
| `coordination`과 `agent-runtime` 스펙을 쓰면서 6단계의 저장이 바뀐다 | 중간 | 6단계는 마이그레이션을 따로 두고, 스펙이 바뀌면 마이그레이션을 더해 고친다. 1~5단계는 영향을 받지 않게 파일을 나눈다 |
| 단계가 뒤로 갈수록 스키마가 바뀌어 앞 단계 테스트가 깨진다 | 중간 | 단계마다 `npm run check` 전체를 돌리고, 스키마는 마이그레이션을 더하는 방식으로만 바꾼다 |
| 닫기, 묶음, 맡긴 일의 규칙 조합이 많아 테스트가 빠진다 | 중간 | 스펙의 표를 그대로 테스트 표로 옮긴다 |
| 빌드 없이 실행하느라 쓸 수 없는 TypeScript 문법이 있다 | 낮음 | 작업 1에서 `tsc` 설정으로 지워지는 문법만 허용한다 |
