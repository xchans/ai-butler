# Capability Map: AI Butler

[AI Butler의 목표](../intent/ai-butler.md)를 따로 만들고 검증할 수 있는 모듈로 나눈 지도다. 모듈마다 스펙을 하나씩 쓰고(`docs/spec/SPEC-<module id>.md`) 아래 순서대로 만든다. 모듈 사이의 계약은 제공하는 쪽 모듈의 스펙에 적는다. 용어는 [요청 처리 원칙](../intent/request-handling-principles.md)을 따른다.

## 단계

목표 문서의 "만드는 순서"를 세 단계로 나눈다.

- **첫 버전** — 사용자가 대화로 여러 일을 맡기고, 비서가 AI 팀원에게 병렬로 배정한 일의 진척을 목록에서 본다. 결정이 필요하면 목록이나 대화에서 답하고, 맡긴 결과가 확인되면 비서가 알린다. 대화에서 짚은 Slack 스레드와 Jira 티켓을 요청에 연결해 끝날 때까지 변경을 따라간다. 사용자가 정정한 내용과 함께 정한 개선을 다음 유사 업무에 반영한다.
- **확장** — 새 채널을 더하고, 연결된 채널을 살펴 사용자가 맡기지 않은 요청을 찾아 등록한다. 사용자 차례인 일에 자료를 미리 붙이고, 맡긴 범위 안에서 비서가 다른 사람에게 직접 연락한다.
- **마지막** — 비서가 스스로 처리 경험을 돌아보고 판단과 절차를 고친다.

## 전제

- 사용자 한 명이 자신의 Mac에서 상시 실행하고, 사용자 본인의 자격으로 기록을 읽는다.
- 첫 버전에서 요청이 들어오는 채널은 사용자와의 대화다. Slack과 Jira는 사용자가 대화에서 짚은 스레드와 티켓만 읽어 요청에 연결하고 변경을 따라간다. 채널 전체를 살펴 새 요청을 찾는 일은 확장 단계에서 한다.
- AI 팀원은 Claude Code, Codex 같은 코딩 에이전트의 세션으로 실행한다. 첫 버전은 실행 도구 하나로 여러 팀원을 병렬로 돌리고, 다른 도구는 같은 계약의 구현을 더해 붙인다. 팀원의 역할과 지침, 처리 경험은 세션이 바뀌어도 비서가 이어 준다. 어느 도구로 시작하고 세션을 어떻게 띄우고 잇는지, 팀원이 어떤 자격으로 실행되는지는 `agent-runtime` 스펙에서 정한다.
- 사용자가 비서에게 말로 전할 때는 코딩 에이전트 세션에서 비서 스킬을 쓴다. 말을 해석하는 일은 그 세션의 에이전트가 하고, 비서는 스킬이 호출하는 명령으로 정리된 입력을 받는다. 웹 화면 안의 대화창은 첫 버전에서 만들지 않는다.
- 사용자는 웹 화면에서 목록을 보고 답하고 정정한다. 비서가 먼저 전하는 질문과 알림은 웹 화면에 남기고, 화면이 닫혀 있어도 Mac 알림으로 알린다.
- 배포 기록이나 로그처럼 작업 결과를 확인하는 자료는 채널로 붙이지 않는다. 팀원이 작업하면서 직접 조회하고, 결과와 함께 근거로 보고한다. 사용자나 다른 담당이 처리한 일은 연결된 기록으로 확인한다.
- 첫 버전에서 비서와 팀원은 채널에 글을 쓰거나 다른 사람에게 연락하지 않는다. 사용자에게 보내는 알림과 질문, 팀원에게 보내는 지시는 여기에 들지 않는다. 회신까지 맡긴 요청은 접수할 때 회신은 사용자 몫이라고 알리고 회신을 사용자의 작업으로 남기며, 실제로 전달된 기록이 연결된 뒤에 닫는다.
- 첫 버전에서 사용자의 결정을 물을 때는 그 요청에 이미 있는 근거와 무엇을 정해야 하는지, 다음에 일어날 일을 함께 보여 준다. 다른 곳의 자료를 미리 조회해 붙이고 최신으로 유지하는 일은 확장 단계의 `preparation`이 한다.
- 첫 버전에서 팀원에게 배정하려면 요청마다 사용자가 맡겨야 한다. 업무 지침으로 미리 맡겨 둔 범위를 새 요청에 자동으로 적용하는 일은 확장 단계에서 다룬다.
- 사용자가 비서를 거치지 않고 따로 연 코딩 에이전트 세션의 기록을 읽어 진행한 일을 찾는 것은 첫 버전에서 다루지 않는다.
- 첫 버전을 점검할 사례는 한 대화에서 서로 다른 두 요청을 맡기는 사례다. 한 요청에는 Jira 티켓이 연결돼 그 변경이 반영되고, 한 팀원이 승인을 기다리는 동안 다른 팀원은 계속 진행하며, 사용자가 목록이나 대화에서 한 번 답하면 해당 팀원만 이어 간다. 근거가 일부만 오면 보완을 맡기고, 맡긴 부분만 끝나면 누구에게 무엇이 남았는지 알리며, 회신이 남은 요청은 닫히지 않는다. 사례 문서의 [한 대화에서 맡긴 두 가지 일](../ideas/request-handling-cases.md#한-대화에서-맡긴-두-가지-일)이 이 사례다.

## 공통 규약

기술 스택, 명령, 디렉터리 구조, 코드 스타일, 테스트 전략, 경계와 상시 실행 프로세스·모델 호출 방식은 모든 모듈이 따르는 규약이다. 모듈로 두지 않고 `docs/spec/SPEC.md`에 적는다. 모듈을 조합해 실행하는 진입점(`src/app/`)도 모듈이 아니고 공통 규약에서 정한다. 모듈별 스펙은 그 모듈의 목적과 계약, 완료 조건만 적는다.

## 모듈

| Module id | 단계 | 책임 | Depends on |
|---|---|---|---|
| `request-ledger` | 첫 버전 | 업무 원장. 요청, 작업, 담당, 차례, 상태, 긴급도와 중요도, 약속한 결과, 근거 기록을 저장하고 변경 이력을 남긴다. 맡긴 범위, 팀원에게 배정한 작업과 기대한 결과, 팀원이 보낸 결과와 근거, 비서가 확인한 내용, 사용자의 답·승인·방향 변경, 요청별 진척을 함께 보관한다. 사용자가 정한 값을 비서의 판단이 덮어쓰지 못하게 하고, 기록에서 확인한 완료와 사용자가 표시한 완료를 구분한다. 질문과 알릴 일도 요청과 함께 보관한다. | — |
| `channel-connectors` | 첫 버전 | 채널과 업무 기록을 읽어 공통 형식으로 넘기는 커넥터 계약과 Slack·Jira 구현. 첫 버전에서는 짚어 준 스레드와 티켓을 읽고 그 변경을 따라간다. 채널 전체를 살피는 일과 새 채널은 확장 단계에서 커넥터에 더한다. | — |
| `agent-runtime` | 첫 버전 | AI 팀원의 세션을 띄우고, 지시와 사용자의 결정을 전달하고, 진행 보고와 결과·근거·질문을 어느 배정에서 온 것인지와 함께 돌려주는 계약과 첫 실행 도구의 구현. 독립적인 작업을 병렬로 실행하고, 중단된 작업을 새 세션에서 이어 간다. 넘겨받은 도구와 권한의 범위 안에서만 실행하고, 그 범위를 적용할 수 없으면 실행하지 않고 돌려준다. 이어 가는 세션에도 같은 범위를 적용한다. | — |
| `teammates` | 첫 버전 | 팀원 명부. 팀원별 역할과 지침, 도구와 권한, 처리 경험을 관리하고 작업에 맞는 팀원을 고른다. 필요한 역량을 가진 팀원이 없으면 이미 허용된 도구와 권한 안에서 새 역할의 팀원을 더하고, 추가 권한이나 승인이 필요하면 그 사실을 돌려준다. | — |
| `worklist-ui` | 첫 버전 | 웹 화면과 Mac 알림. 여러 요청의 진척과 내 차례, 처리할 순서를 보여 주고, 요청을 열면 작업별 담당과 진행, 팀원이 보낸 결과와 근거, 비서가 확인한 내용을 보여 준다. 사용자의 답·승인·정정·보류·방향 변경을 받고, 원장에 남은 질문과 알릴 일(내 차례, 확인할 사항, 확인된 결과, 닫힌 요청)을 전한다. 새 요청 알림은 확장 단계에서 더한다. 대기·보류·끝내기로 정한 요청을 구분하고, 완료와 철회·이관·맡지 않음·요청 아님, 기록에서 확인한 완료와 사용자가 표시한 완료를 구분해 보여 준다. 첫 버전에는 전체 목록과 요청 안 작업의 그래프를 넣고, 칸반보드는 원장이 계산하는 요청의 상태를 열로 쓰는 후속 화면이다. | `request-ledger` |
| `intake-triage` | 첫 버전 | 접수와 묶기. 맡긴 말과 짚어 준 기록이 새 요청인지 이미 있는 요청에 속하는지 가려 등록하거나 연결하고, 목록에서 바로 알아볼 수 있는 제목과 작업, 차례, 긴급도와 중요도, 약속한 결과를 정한다. 판단할 수 없는 것은 질문으로 남긴다. | `request-ledger`, `channel-connectors` |
| `conversation` | 첫 버전 | 사용자가 비서에게 말로 전하는 창구. 코딩 에이전트에 설치하는 비서 스킬과 그 스킬이 호출하는 명령이다. 일을 맡기고 맡길 범위를 정하는 말, Slack 스레드나 Jira 티켓을 짚어 주는 말, 질문에 대한 답·승인·정정·방향 변경을 받아 웹 화면과 같은 원장 계약으로 남기고, 목록과 요청을 조회해 답한다. 어느 요청에 속하는지와 제목은 `intake-triage`의 판단에 맡긴다. | `request-ledger`, `channel-connectors`, `intake-triage` |
| `coordination` | 첫 버전 | 맡긴 범위 안에서 다음 작업을 정하고, 맞는 팀원에게 할 일과 기대하는 결과를 전달해 독립적인 작업을 병렬로 진행시킨다. 배정할 때는 명부가 준 팀원의 허용 범위를 이번에 맡긴 범위와 사용자의 승인에 대조해, 그 안에서만 실행하게 한다. 팀원의 진행 보고와 질문, 결과와 근거를 해당 요청과 작업에 기록한다. 팀원의 질문에는 기록에서 답할 근거가 충분하면 답하고 그 판단과 근거를 요청에 남기며, 아니면 사용자에게 묻는다. 사용자의 결정과 보류·방향 변경을 관련 팀원에게 전달하고, 확인에서 부족하다고 나온 부분은 보완을 맡긴다. 사용자가 판단·승인하거나 직접 조치할 차례가 되면 알릴 일을 남기고, 거듭 보완해도 풀리지 않으면 어디서 막혔는지 남긴다. 기한과 선후 관계, 최근 진행을 살펴 지연이 후속 작업이나 기한에 영향을 주는 배정을 찾아 팀원에게 상황을 묻거나 사용자에게 필요한 결정을 알린다. 범위 밖에서 필요한 조치는 실행하지 않고 목록에 드러낸다. | `request-ledger`, `teammates`, `agent-runtime` |
| `progress-verification` | 첫 버전 | 원장에 기록된 팀원의 결과와 근거, 연결된 기록의 변경을 기대한 결과와 약속한 결과에 대조하고, 확인한 내용을 보고와 구분해 남긴다. 확인된 만큼 작업과 요청의 상태와 진척을 옮기고, 부족한 부분을 남기며, 맡긴 범위의 결과가 확인되면 근거와 남은 일을 알릴 일로 남긴다. 약속한 결과가 이루어진 것을 확인하면 요청을 닫는다. 완료와 철회·이관·맡지 않음을 구분하고, 사용자가 정해 둔 재개 조건이 이루어지면 보류를 푼다. 스스로 풀 수 없으면 무엇을 확인하지 못했는지 남기고 묻는다. | `request-ledger`, `channel-connectors` |
| `corrections` | 첫 버전 | 사용자의 정정과 사용자와 함께 돌아보며 정한 개선을 다음 유사 업무의 판단과 팀원의 지침에 반영한다. 그 요청에만 해당하는 지시는 다른 요청으로 넓히지 않는다. 어떤 정정이나 개선 때문에 판단이나 절차가 달라졌는지 보여 주고 되돌릴 수 있게 하며, 권한과 승인 조건은 넓히지 않는다. 이번 요청에만 해당하는 지시인지 다음부터 적용할 개선인지는 `conversation`과 `worklist-ui`가 구분해 받아 원장에 남기고, `corrections`는 원장에서 읽는다. | `request-ledger`, `teammates`, `intake-triage`, `coordination`, `progress-verification` |
| `preparation` | 확장 | 사용자 차례이거나 다음에 사용자 차례가 될 일에 판단과 조치에 필요한 자료를 조회해 붙이고, 차례가 오면 최신 내용으로 다시 확인한다. | `request-ledger`, `channel-connectors` |
| `request-discovery` | 확장 | 연결된 채널을 살펴 사용자가 맡기지 않은 요청을 찾아 등록하고 알린다. 처리할 요청인지 가리고, 묶기는 `intake-triage`에 맡긴다. | `request-ledger`, `channel-connectors`, `intake-triage` |
| `outreach` | 확장 | 맡긴 범위 안에서 요청자와 담당자, 결과를 알리기로 한 사람에게 비서가 직접 연락한다. 누구에게 무엇을 보냈는지 요청에 남기고, 이미 전달된 결과는 다시 보내지 않는다. 보내는 계약은 읽는 계약과 구분해 `channel-connectors`에 더한다. | `request-ledger`, `channel-connectors`, `coordination` |
| `self-review` | 마지막 | 비서가 스스로 처리 경험을 돌아보고 판단과 절차를 고친다. | `corrections`, `coordination` |

판단 모듈(`intake-triage`, `coordination`, `progress-verification`)은 서로 직접 부르지 않고 원장을 거쳐 이어진다. 확인에서 부족하다고 남긴 것을 `coordination`이 읽어 보완을 맡기고, `conversation`이 남긴 결정을 `coordination`이 읽어 팀원에게 전달한다. 연결한 기록에서 요청자가 요구를 바꾸면 `intake-triage`가 약속한 결과와 작업의 변경을 남기고, 새로 맡겨야 하는 범위는 사용자가 승인한 뒤 `coordination`이 배정하며, `progress-verification`은 바뀐 약속에 대조한다. 웹 화면과 대화 어느 쪽에서 한 보류와 방향 변경도 같은 원장 기록이 된다. `worklist-ui`와 `conversation`은 화면과 명령이 하는 일을 담은 모듈이고, 웹 서버와 명령의 실행 파일은 `src/app/`의 진입점이다. `corrections`가 보여 주고 되돌리는 것도 진입점이 두 창구에 이어 준다. 이 모듈들을 차례로 돌리는 일은 `src/app/`의 상시 실행 프로세스가 하고, 한 팀원을 기다리느라 다른 팀원의 보고와 사용자의 답을 처리하지 못하는 일이 없게 한다.

## 모듈 사이의 정정 계약

- **그 요청에 대한 정정**은 `request-ledger`가 지킨다. 판단 모듈은 원장을 거쳐서만 값을 쓰고, 원장은 사용자의 지시(보류, 긴급도와 중요도, 처리할 순서, 묶음, 직접 표시한 완료, 끝내기로 한 결정)를 비서의 판단으로 바꾸지 않는다. 보류는 사용자가 풀거나, 사용자가 미리 정한 재개 조건이 이루어진 것을 `progress-verification`이 확인했을 때 푼다. 상태를 바로잡은 것은 이후 새 기록이 생기면 다시 옮길 수 있다. 이 계약은 첫 모듈부터 적용한다.
- **다음 유사 업무에 대한 적용**은 `corrections`가 맡는다. 판단 모듈(`intake-triage`, `coordination`, `progress-verification`)과 `teammates`는 스펙에서 적용할 지침을 받는 입력을 정의하고, `corrections`가 그 입력을 채운다.

## 만드는 순서

첫 버전: `request-ledger` → `worklist-ui`, `channel-connectors`, `agent-runtime`, `teammates` → `intake-triage` → `conversation`, `coordination`, `progress-verification` → `corrections`

확장: `preparation`, `request-discovery`, `outreach`

마지막: `self-review`

쉼표로 묶은 모듈은 서로 의존하지 않아 함께 만들 수 있다.
