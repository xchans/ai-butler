# Capability Map: AI Butler

[AI Butler의 목표](../intent/ai-butler.md)를 따로 만들고 검증할 수 있는 모듈로 나눈 지도다. 모듈마다 스펙을 하나씩 쓰고(`docs/spec/SPEC-<module id>.md`) 아래 순서대로 만든다. 모듈 사이의 계약은 제공하는 쪽 모듈의 스펙에 적는다. 용어는 [요청 처리 원칙](../intent/request-handling-principles.md)을 따른다.

## 전제

- 사용자 한 명이 자신의 Mac에서 상시 실행하고, 사용자 본인의 자격으로 채널과 기록을 읽는다.
- 첫 버전의 채널과 기록은 Slack, Jira, 사용자다. Slack과 Jira는 비서가 살피고, 사용자 채널은 사용자가 비서에게 직접 맡기는 말이 들어오는 채널이다. 첫 버전을 점검할 사례는 [슬랙과 Jira에 걸친 CS팀 VOC 요청](../ideas/request-handling-cases.md#슬랙과-jira에-걸친-cs팀-voc-요청)이다.
- 이메일은 커넥터를 추가해 붙인다. AWS 배포 기록과 WAS 로그는 채널로 붙이지 않는다. 사례 문서에서 처음 자동화하고 싶은 일로 꼽은 서비스별 ECS 배포 기록과 WAS 로그 확인은 에이전트가 작업을 수행하면서 직접 조회해 확인하고, 그 방법은 이 확인을 처음 다루는 스펙에서 정한다.
- 사용자는 웹 화면에서 목록을 보고 정정한다.
- 사용자가 비서에게 말로 전할 때는 Claude Code, Codex 같은 코딩 에이전트 세션에서 비서 스킬을 쓴다. 말을 해석하는 일은 그 세션의 에이전트가 하고, 비서는 스킬이 호출하는 명령으로 정리된 입력을 받는다. 비서가 먼저 전하는 질문과 알림은 웹 화면에 남기고, 화면이 닫혀 있어도 Mac 알림으로 알린다. 웹 화면 안의 대화창은 첫 버전에서 만들지 않는다.
- 코딩 에이전트의 세션 기록을 채널처럼 읽어 사용자가 직접 진행한 일을 찾는 것은 첫 버전에서 다루지 않는다. 필요해지면 커넥터로 붙인다.
- 추적 모듈은 채널과 기록을 읽기만 한다. 채널에 글을 쓰거나 다른 사람에게 연락하는 일은 실행 조율부터 다룬다. 사용자에게 보내는 알림과 질문은 여기에 들지 않는다.

## 공통 규약

기술 스택, 명령, 디렉터리 구조, 코드 스타일, 테스트 전략, 경계와 상시 실행 프로세스·모델 호출 방식은 모든 모듈이 따르는 규약이다. 모듈로 두지 않고 `docs/spec/SPEC.md`에 적으며, 첫 모듈의 스펙과 함께 쓴다. 모듈을 조합해 실행하는 진입점(`src/app/`)도 모듈이 아니고 공통 규약에서 정한다. 모듈별 스펙은 그 모듈의 목적과 계약, 완료 조건만 적는다.

## 모듈

| Module id | 영역 | 책임 | Depends on |
|---|---|---|---|
| `request-ledger` | 추적 | 요청, 작업, 담당, 차례, 상태, 긴급도와 중요도, 약속한 결과, 근거 기록을 저장하고 변경 이력을 남긴다. 사용자가 정한 값은 사실을 바로잡은 것과 지시를 구분해 보관하고, 지시는 사용자가 바꾸거나 사용자가 미리 정한 조건이 이루어질 때까지 비서의 판단이 덮어쓰지 못하게 한다. 기록에서 확인한 완료와 사용자가 표시한 완료, 아직 확인하지 못한 사항과 사용자에게 물을 질문, 알릴 일도 요청과 함께 보관한다. | — |
| `channel-connectors` | 추적 | 채널과 업무 기록을 읽어 공통 형식으로 넘기는 커넥터 계약과 Slack·Jira 구현. 새 채널과 기록은 커넥터를 추가해 붙인다. 사용자 채널은 살피는 채널이 아니어서 커넥터를 두지 않고, `conversation`이 받은 말을 같은 공통 형식으로 넘긴다. | — |
| `worklist-ui` | 추적 | 웹 화면과 Mac 알림. 내 차례인 일과 처리할 순서, 요청별 작업·담당·진행·근거를 보여 준다. 같은 원장 조회 결과를 전체 목록, 칸반보드, 요청 안 작업의 그래프처럼 여러 보기로 보여 줄 수 있게 구성한다. 첫 버전에는 전체 목록과 요청 안 작업의 그래프를 넣고, 칸반보드는 원장이 계산하는 요청의 상태(접수, 진행 중, 닫힘)를 열로 쓰며 첫 버전 뒤에 넣는다. 대기·보류·이관을 구분하고, 일부 작업이 멈춰 있어도 지금 할 수 있는 작업을 드러낸다. 완료와 철회·이관·맡지 않음·요청 아님, 기록에서 확인한 완료와 사용자가 표시한 완료를 구분해 보여 준다. 사용자의 정정을 받고, 원장에 남은 질문과 알릴 일(새 요청, 내 차례, 확인할 사항, 닫힌 요청)을 사용자에게 전하고 답을 받는다. | `request-ledger` |
| `intake-triage` | 추적 | 접수와 묶기. 새 기록이 처리할 요청인지, 이미 있는 요청에 속하는지 가려 등록하거나 합치고, 목록에서 바로 알아볼 수 있는 제목과 작업, 차례, 긴급도와 중요도, 약속한 결과를 정한다. 판단할 수 없는 것은 질문으로 남긴다. | `request-ledger`, `channel-connectors` |
| `progress-verification` | 추적 | 기록에서 확인된 만큼 작업과 요청의 상태를 옮기고, 약속한 결과와 대조해 요청을 닫고 닫았음을 알린다. 완료와 철회·이관·맡지 않음을 구분한다. 철회는 철회한 기록을, 맡지 않음과 이관은 그 결정이 요청자에게 전달된 기록을 확인한 뒤에 닫는다. 이관은 넘겨받는 쪽이 인수한 기록까지 확인하거나 사용자가 인수까지 끝났다고 직접 확인했을 때 닫고, 사용자 확인으로 닫았으면 그 점을 남긴다. 사용자가 보류에 미리 정해 둔 재개 조건이 이루어진 것을 확인하면 보류를 푼다. 기록이 어긋나거나 접근할 수 없어 스스로 풀 수 없으면 무엇을 확인하지 못했는지 남기고 묻는다. | `request-ledger`, `channel-connectors`, `intake-triage` |
| `preparation` | 추적 | 사용자 차례이거나 다음에 사용자 차례가 될 일에 판단과 조치에 필요한 자료를 조회해 붙이고, 차례가 오면 최신 내용으로 다시 확인한다. | `request-ledger`, `channel-connectors`, `intake-triage` |
| `conversation` | 추적 | 사용자가 비서에게 말로 전하는 창구. 코딩 에이전트에 설치하는 비서 스킬과 그 스킬이 호출하는 명령이다. 사용자가 직접 맡기는 일은 사용자 채널의 기록으로 받아 요청으로 접수하고, 이미 있는 요청에 속하는지와 제목은 `intake-triage`의 판단에 맡긴다. 말로 한 정정과 지시(보류와 재개 조건 포함)는 웹 화면에서 한 정정과 같은 원장 계약으로 반영하며, 목록과 요청을 조회해 답한다. 비서가 남긴 질문에도 여기서 답할 수 있다. 실행 조율에서는 맡기기와 방향 바꾸기도 이 창구로 받는다. | `request-ledger`, `channel-connectors`, `intake-triage` |
| `corrections` | 추적 | 사용자의 정정과 사용자와 함께 돌아보며 정한 변화를 다음 유사 업무의 판단과 준비에 적용한다. 함께 정한 변화는 사용자가 비서 스킬의 명령으로 기록한다. 그 요청에만 해당하는 지시는 다른 요청으로 넓히지 않는다. 어떤 정정이나 변화 때문에 판단이 달라졌는지, 적용한 뒤 효과가 있었는지 보여 주고 되돌릴 수 있게 한다. | `request-ledger`, `worklist-ui`, `intake-triage`, `progress-verification`, `preparation`, `conversation` |
| `execution-coordination` | 실행 조율 | 맡긴 범위, AI 팀원의 역할·지침·도구·권한, 작업 배정과 병렬 실행, 결과 확인, 맡긴 범위 안의 연락. 팀원의 작업이 끝날 때마다 어느 팀원의 어떤 작업이 끝났고 확인한 결과와 남은 일이 무엇인지 사용자에게 회신한다. | 추적 모듈 전체 |
| `self-review` | 배우기 | 비서가 스스로 처리 경험을 돌아보고 판단과 절차를 고친다. | `corrections`, `execution-coordination` |

`execution-coordination`은 모듈 하나가 아니라 영역이다. 추적을 마치고 착수할 때 이 지도에서 모듈로 다시 나눈 뒤 스펙을 쓴다.

## 모듈 사이의 정정 계약

- **그 요청에 대한 정정**은 `request-ledger`가 지킨다. 판단 모듈은 원장을 거쳐서만 값을 쓰고, 원장은 사용자의 지시(보류, 긴급도와 중요도, 처리할 순서, 묶음, 직접 표시한 완료)를 비서의 판단으로 바꾸지 않는다. 보류는 사용자가 풀거나, 사용자가 미리 정한 재개 조건이 이루어진 것을 `progress-verification`이 확인했을 때 푼다. 상태를 바로잡은 것은 이후 새 기록이 생기면 다시 옮길 수 있다. 이 계약은 첫 모듈부터 적용한다.
- **다음 유사 업무에 대한 적용**은 `corrections`가 맡는다. 판단 모듈(`intake-triage`, `progress-verification`, `preparation`)은 스펙에서 적용할 지침을 받는 입력을 정의하고, `corrections`가 그 입력을 채운다.

## 만드는 순서

`request-ledger` → `channel-connectors`, `worklist-ui` → `intake-triage` → `progress-verification`, `preparation`, `conversation` → `corrections` → `execution-coordination` → `self-review`

쉼표로 묶은 모듈은 서로 의존하지 않아 함께 만들 수 있다.
