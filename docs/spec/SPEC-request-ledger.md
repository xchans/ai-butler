# Spec: request-ledger — V1

[capability map](capability-map.md)의 첫 모듈이다. 기술 스택, 명령, 코드 스타일, 테스트 전략, 경계는 [공통 규약](SPEC.md)을 따른다.

## 목적

`request-ledger`는 업무 목록의 원장이다. 요청과 작업, 근거 기록을 저장하고, 누가 무엇을 근거로 값을 바꿨는지 남긴다. 화면과 판단 모듈은 모두 이 원장을 거쳐 읽고 쓴다.

원장은 판단하지 않는다. 어떤 기록이 어느 요청에 속하는지, 작업이 끝났는지는 판단 모듈과 사용자가 정하고, 원장은 그 값을 저장하면서 두 가지를 지킨다.

- **사용자가 정한 것이 비서의 판단보다 앞선다.** 사용자의 지시는 어느 모듈이 쓰더라도 비서의 판단으로 바뀌지 않는다. 이 규칙을 모듈마다 따로 구현하지 않도록 원장이 쓰기를 거부한다.
- **완료 표시를 믿을 수 있다.** 비서는 근거 없이 끝났다고 쓸 수 없고, 기록에서 확인한 것과 사용자가 직접 확인한 것은 구분해 저장한다.

사용하는 쪽은 `worklist-ui`, `intake-triage`, `progress-verification`, `preparation`, `conversation`, `corrections`다. 이 모듈은 모델을 부르지 않고 채널에 접근하지 않는다.

## 용어 대응

용어의 뜻은 [요청 처리 원칙](../intent/request-handling-principles.md)을 따른다. 판본, 확인할 사항, 알릴 일, 준비 자료, 닫힘 예정은 원칙 문서의 내용을 저장하려고 이 스펙에서 붙인 이름이다.

| 용어 | 코드 | 용어 | 코드 |
|---|---|---|---|
| 요청 | `request` | 근거 기록 | `record` |
| 작업 | `task` | 판본 | `revision` |
| 담당 | `assignee` | 기록과 요청의 연결(묶음) | `link` |
| 차례 | `turn` | 확인할 사항 | `openItem` |
| 보류 | `hold` | 알릴 일 | `notice` |
| 약속한 결과 | `promisedOutcome` | 준비 자료 | `material` |
| 닫힘 | `closure` | 변경 이력 | `change` |
| 닫힘 예정 | `pendingClosure` | | |

## 저장하는 것

- **요청** — 제목, 요청자, 약속한 결과(해 주기로 한 일과 결과를 알릴 사람들), 기한, 긴급도와 중요도(각각 높음, 보통, 낮음), 사용자가 정한 처리 순서, 열림·닫힘, 닫힘 예정, 닫힘. 제목, 요청자, 약속한 결과, 기한, 긴급도, 중요도는 값 하나를 저장하고, 바뀐 내역은 변경 이력에 남긴다. 값마다 두 가지를 함께 저장한다. **정한 주체**는 지금 값을 마지막으로 쓴 쪽(사용자 또는 비서)이고, 빈 값에는 없다. **사용자 지정**은 사용자가 그 값을 정해 두었다는 표시로, 사용자가 값을 쓰면 걸리고 사용자가 풀 때까지 남으며 걸린 시각을 함께 저장한다. 요청을 등록하거나 나눌 때는 사용자가 명시한 값과 비서가 정한 값을 함께 받아, 사용자가 명시한 값에만 사용자 지정을 건다. 제목은 비워 둘 수 없고, 나머지 값은 접수할 때 정해지지 않았으면 비워 둘 수 있다. 처리할 요청인지 아직 정해지지 않았으면 미정으로 표시해 등록하고, 목록에는 그대로 보인다.
- **작업** — 속한 요청, 할 일, 담당, 상태, 대기 대상(누구에게 무엇을 요청했는지), 먼저 끝나야 하는 작업, 완료를 확인한 방식, 사용자가 정한 차례.
- **근거 기록과 판본** — 기록은 채널이나 업무 도구에 있는 원본 하나다. 출처(예: `slack`, `jira`)와 출처 안의 id가 같으면 같은 기록이다. 판본은 그 원본을 읽은 내용으로, 원본 그대로의 본문, 주소, 작성자, 원본에서 생기거나 바뀐 시각, 읽어 온 시각을 담는다. 아래에서는 원본에서 생기거나 바뀐 시각을 원본 시각이라고 한다. 원본이 바뀌면 판본을 더하고 이전 판본은 지우지 않으므로, 원본이 어떻게 바뀌어 왔는지가 이력으로 남는다. 판본은 기록과 원본 시각으로 구별한다. 원본 시각이 같은 판본을 다시 읽어 와도 판본이 늘지 않고, 원본 시각이 다르면 본문이 같아도 새 판본이다.
- **사용자 채널의 기록** — 사용자도 채널 하나다. 사용자가 비서에게 일을 직접 맡기면서 한 말을 이 채널의 기록으로 저장하고, 아래에서는 직접 맡긴 말이라고 한다. 출처는 `conversation`이고 작성자는 사용자, 원본 시각은 말한 시각이며 주소는 없다. 출처 안의 id는 창구가 붙이고, 같은 id로 다시 접수해도 기록은 하나다. 이 기록은 접수 원본으로만 연결하고, 어떤 쓰기의 근거로도 달 수 없다. 이미 있는 요청에 일을 더 맡긴 말도 그 요청의 접수 원본으로 연결한다. 사용자가 말로 한 정정과 확인은 기록이 아니라 사용자의 쓰기로 반영한다.
- **연결** — 기록이 어느 요청(필요하면 어느 작업)에 속하는지와 그 역할. 역할은 접수 원본, 진행 기록, 완료 근거, 결과 전달 넷이다. 한 기록이 여러 요청에 연결될 수 있다. 사용자가 끊은 연결은 끊었다는 사실을 남긴다.
- **근거** — 완료, 닫힘, 값 변경에 단 근거는 기록이 아니라 판본을 가리킨다. 원본이 나중에 바뀌어도 판단할 때 본 내용이 남는다.
- **보류** — 요청이나 작업에 사용자가 건 멈춤과 재개 조건.
- **확인할 사항** — 요청이나 작업에 달린 미결 사항. 종류는 질문(판단할 수 없어 사용자에게 묻는 것), 미확인(기록이 어긋나거나 접근할 수 없어 확인하지 못한 것), 어긋남(사용자의 표시와 기록이 다른 것) 셋이다. 내용, 선택지, 답, 해결 여부를 저장한다.
- **알릴 일** — 사용자에게 전할 일. 종류는 새 요청, 내 차례, 확인할 사항, 닫힘이다. 만든 시각, 전한 시각, 사용자가 본 시각을 저장한다. 전하는 일은 `worklist-ui`가 한다.
- **준비 자료** — 요청이나 작업에 붙인 자료. 제목, 내용, 출처, 마지막으로 확인한 시각.
- **변경 이력** — 모든 쓰기의 기록. 순번, 시각, 쓴 주체, 대상, 이전 값과 새 값, 근거, 사유. 비서의 판단과 사용자의 정정을 나중에 비교해 판단을 고치는 데 쓴다.

## 상태

**작업의 상태**는 다섯 가지다.

| 상태 | 코드 | 뜻 |
|---|---|---|
| 할 일 | `todo` | 아직 시작하지 않았다 |
| 진행 중 | `in_progress` | 담당이 하고 있다 |
| 대기 | `waiting` | 담당이 다른 주체의 조치를 기다린다. 대기 대상을 함께 적는다 |
| 완료 | `done` | 끝났다. 기록에서 확인했는지 사용자가 표시했는지 함께 적는다 |
| 취소 | `cancelled` | 하지 않기로 했다. 사유를 함께 적는다 |

**요청**은 열림(`open`)과 닫힘(`closed`) 둘이다. 닫힘의 종류는 완료(`completed`), 철회(`withdrawn`), 이관(`transferred`), 맡지 않음(`declined`), 요청 아님(`not_a_request`)이다.

**보류**는 상태가 아니라 상태 위에 얹는 표시다. 보류 중에도 작업의 상태는 기록에 따라 계속 바뀔 수 있고, 보류를 풀면 그때의 상태가 드러난다. 요청을 보류하면 그 요청의 모든 작업이 보류된 것으로 본다.

**닫힘 예정**은 철회가 확인됐거나 사용자가 맡지 않거나 넘기기로 정했지만 아직 닫을 조건을 채우지 못한 요청에 붙는다. 종류와 정한 시각, 남은 확인을 적는다. 닫힘 예정이 붙을 때 끝나지 않은 작업은 멈춰야 하는 작업이 된다. 닫는 데 필요한 작업(요청자에게 알리기, 인수 확인 받기)은 닫는 작업으로 표시해 더하고, 사용자가 계속하라고 한 작업은 멈춰야 하는 작업에서 빠진다.

### 조회할 때 계산하는 값

끝나지 않은 작업은 아래에서 먼저 맞는 줄 하나로 표시한다.

| 순서 | 조건 | 표시 | 차례 |
|---|---|---|---|
| 1 | 요청이 닫혔다 | 닫힌 요청의 남은 작업 | 없음 |
| 2 | 요청이 닫힘 예정이고, 닫는 작업이 아니며, 계속하라는 지시가 없다 | 멈춰야 함 | 없음 |
| 3 | 작업이나 요청이 보류됐다 | 보류 | 없음 |
| 4 | 먼저 끝나야 하는 작업이 취소됐다 | 선행 작업 취소됨 | 없음 |
| 5 | 먼저 끝나야 하는 작업이 끝나지 않았다 | 선행 작업 대기 | 없음 |
| 6 | 상태가 대기다 | 대기 | 대기 대상 |
| 7 | 상태가 할 일이나 진행 중이다 | 진행할 수 있음 | 담당 |

- 사용자가 작업의 차례를 직접 정했으면 4~7에서 계산한 차례 대신 그 값을 쓴다. 1~3에 해당하는 작업은 사용자가 정한 차례가 있어도 차례가 없다.
- **요청의 차례**는 끝나지 않은 작업들의 차례를 모은 것이다. 사용자가 들어 있으면 내 차례인 요청이다. 요청의 차례는 따로 저장하지 않는다. 사용자가 요청의 차례를 바로잡으려면 작업의 차례를 정하고, 끝나지 않은 작업이 없으면 담당을 정한 작업을 더한다.
- **다음 작업 미정**은 열린 요청인데 끝나지 않은 작업이 없고 닫힘 예정도 아닌 경우다. 비서가 추측으로 차례를 채우지 않고 이 표시로 드러낸다.
- 선행 작업이 취소된 작업은 저절로 풀리지 않는다. 의존을 지우거나 그 작업도 취소해야 한다.

## 쓰기 계약

모든 쓰기는 주체를 밝힌다. 주체는 사용자(창구: 웹 화면 또는 스킬)이거나 비서(쓴 모듈 이름)다. "나중 판본"은 원본 시각이 사용자의 정정(요청의 값이면 사용자 지정이 걸린 시각)보다 뒤이고, 그 값에 마지막으로 반영된 근거 판본의 원본 시각보다 앞서지 않는 판본이다. 판본이 늦게 도착해도 값이 예전으로 되돌아가지 않는다.

| 값 | 사용자가 쓰면 | 비서가 쓰면 |
|---|---|---|
| 보류 | 걸고 풀 수 있다. 재개 조건을 적을 수 있다 | 걸 수 없다. 재개 조건이 이루어졌음을 보여 주는 근거를 달았을 때만 풀 수 있다 |
| 긴급도, 중요도, 요청자 | 값을 쓰면 사용자 지정이 걸린다. 사용자 지정을 풀 수 있다 | 사용자 지정이 걸린 값은 바꿀 수 없다 |
| 처리 순서 | 정하고 지울 수 있다 | 쓸 수 없다 |
| 묶음 | 기록과 작업을 옮기고, 연결을 끊고, 요청을 합치고 나눌 수 있다. 사용자가 정한 것으로 표시한다 | 사용자가 옮긴 기록과 작업을 옮길 수 없다. 사용자가 정한 연결을 끊을 수 없고, 사용자가 끊은 연결을 다시 만들 수 없다. 사용자가 나눈 요청을 합칠 수 없고, 사용자가 합친 요청을 나눌 수 없다 |
| 완료 표시 | 근거 없이 작업이나 요청을 끝났다고 표시할 수 있다. 사용자가 표시한 완료로 저장한다 | 근거를 달아야 완료로 쓸 수 있다. 사용자가 표시한 완료를 되돌리거나 그 작업을 다시 시작할 수 없다. 기록이 어긋나면 판단 모듈이 어긋남을 확인할 사항으로 남긴다 |
| 계속하라는 지시 | 닫힘 예정인 요청의 작업에 걸고 풀 수 있다 | 쓸 수 없다 |
| 차례 | 담당과 상태를 그대로 둔 채 작업의 차례를 정하고 지울 수 있다 | 직접 쓸 수 없다. 나중 판본을 근거로 그 작업의 상태, 담당, 대기 대상을 바꾸면 사용자가 정한 차례는 풀린다. 작업이 끝나도 풀린다 |
| 작업의 상태(완료 제외), 담당, 대기 대상 | 그 시점의 값으로 바로 반영한다 | 사용자가 바로잡은 값은 나중 판본을 근거로 달았을 때만 바꿀 수 있다 |
| 약속한 결과, 기한 | 값을 쓰면 사용자 지정이 걸린다. 사용자 지정을 풀 수 있다 | 사용자 지정이 걸린 값은 요청자가 요청을 바꾼 나중 판본을 근거로 달았을 때만 바꿀 수 있다. 바꾼 뒤에도 사용자 지정은 남는다 |
| 제목 | 값을 쓰면 사용자 지정이 걸린다. 사용자 지정을 풀 수 있다 | 사용자 지정이 걸린 제목은 제목을 마지막으로 쓴 뒤에 그 요청에 기록이 연결됐거나 작업이 더해졌을 때만 바꿀 수 있다. 근거는 달지 않아도 되고 원장이 변경 이력의 순번으로 확인한다. 바꾼 뒤에도 사용자 지정은 남는다 |

- 규칙에 어긋난 쓰기는 오류로 거부하고 아무것도 바꾸지 않는다. 한 쓰기에 여러 값이 들어 있고 그중 하나라도 어긋나면 쓰기 전체를 거부하고, 오류에 어긋난 값을 밝힌다. 거부된 쓰기는 변경 이력에 남기지 않고, 호출한 쪽이 오류로 받는다.
- **사용자 지정과 정한 주체** — 사용자 지정을 풀면 값과 정한 주체는 그대로 남고, 그 뒤로 비서가 조건 없이 값을 쓸 수 있다. 비서가 사용자 지정이 걸린 값을 조건을 채워 바꾸면 정한 주체는 비서가 되고 사용자 지정과 걸린 시각은 그대로다. 사용자가 다시 값을 쓰면 걸린 시각이 그때로 바뀐다.
- **제목을 마지막으로 쓴 뒤** — 제목의 값이 바뀌었거나 제목에 사용자 지정이 걸린 마지막 쓰기보다 변경 이력의 순번이 뒤인 쓰기를 말한다. 시각이 같아도 순번이 뒤면 뒤다. 기록 연결, 작업 추가, 다른 요청에서 옮겨 온 기록과 작업, 합쳐서 옮겨 온 기록과 작업을 모두 센다. 같은 쓰기에서 제목과 함께 들어온 것은 세지 않는다. 그래서 합치면서 B의 제목을 가져왔거나 나누면서 새 요청의 제목을 정했으면, 그때 함께 옮겨 온 것으로는 제목을 바꿀 수 없고 그 뒤에 더해진 것이 있어야 한다. 합칠 때 A의 제목이 그대로 남았으면 옮겨 온 것을 센다.
- 값, 정한 주체, 사용자 지정이 모두 그대로인 쓰기는 변경 이력을 남기지 않는다. 비서가 정한 값과 같은 값을 사용자가 쓰거나 사용자 지정만 풀어도 변경 이력이 남는다.
- 쓰기 하나는 값과 변경 이력을 한 트랜잭션으로 저장한다. 확인할 사항에 답하면서 그 답에 따라 값을 바꿀 때는 답과 값 변경을 한 트랜잭션으로 저장하고, 변경 이력에 그 답을 근거로 남긴다.
- 원장은 근거가 달렸는지, 근거로 달 수 있는 기록인지, 시각만 확인한다. 직접 맡긴 말은 근거로 달 수 없다. 나중 판본이 있다는 것은 원장이 쓰기를 받아들이는 조건일 뿐이다. 그 근거가 실제로 무엇을 뜻하고 값을 바꿔야 하는지는 판단 모듈이 정한다. 요청자가 바꾼 범위 가운데 사용자가 해 주기로 한 적 없는 것을 사용자에게 확인하는 일도 판단 모듈이 한다.

### 합치기와 나누기

- **합치기** — B를 A에 합치면 B의 작업, 연결, 보류, 확인할 사항, 준비 자료가 A로 옮겨진다. B에 걸린 요청 보류는 B에서 온 작업들의 보류로 바뀌어, A에 원래 있던 작업으로 번지지 않는다. B는 A로 합쳐졌다는 표시와 함께 남아 B를 찾으면 A가 나온다.
- **합칠 때 요청 단위의 값** — A의 것을 쓴다. A에 사용자 지정이 없고 B에 사용자 지정이 걸린 항목은 B의 값을 가져온다. 이때 정한 주체, 사용자 지정이 걸린 시각, 마지막으로 반영된 근거 판본의 시각도 B의 것을 그대로 가져오고 합친 시각으로 바꾸지 않는다. 양쪽 모두 사용자 지정이 걸려 있고 값이 다르면, 사용자가 합칠 때는 A의 것을 쓰고 비서가 합치려 할 때는 거부한다. 사용자 지정을 푼 값은 여기에 들지 않는다.
- **나누기** — A에서 고른 작업과 연결을 새 요청으로 옮긴다. 그 작업에 딸린 보류, 확인할 사항, 준비 자료가 함께 간다. 새 요청의 제목과 약속한 결과는 나눌 때 정하고(사용자가 나누면서 명시한 값에만 사용자 지정을 건다), A의 요청 단위 값은 A에 남는다. 한 기록을 두 요청에 모두 연결해 둘 수 있다. A 전체가 보류돼 있으면 옮겨 가는 작업은 그 보류와 재개 조건을 물려받는다. 작업 하나를 다른 요청으로 옮길 때도 같다.
- **선후 관계** — 먼저 끝나야 하는 작업은 같은 요청 안에서만 정한다. 작업이 자기 자신을 기다리거나 선후 관계를 따라가면 자기에게 돌아오게 되는 쓰기는 거부한다. 새 요청으로 가는 작업과 남는 작업 사이에 선후 관계가 있으면 나누기를 거부한다. 선후 관계를 지우거나 함께 옮겨야 한다.
- **닫힌 요청** — 닫혔거나 닫힘 예정인 요청은 합치거나 나눌 수 없다. 먼저 다시 열거나 닫힘 예정을 거둔다.
- **사용자의 지시 보존** — 사용자가 끊은 연결과 사용자가 나눈 요청이라는 표시는 합치거나 나눠도 따라간다. 비서의 합치기나 나누기가 사용자가 끊은 연결을 되살리거나 사용자가 나눈 요청을 다시 한 요청에 모으게 되면 거부한다. 사용자가 직접 하면 새 지시로 보고 그 표시를 지운다.
- 합치기와 나누기는 한 트랜잭션이고, 옮긴 것은 모두 변경 이력에 남는다. 변경 이력은 요청을 옮겨도 지워지지 않는다.

### 닫기

요청을 닫으려면 닫힘 종류마다 정해진 확인을 모두 채워야 한다.

| 닫힘 종류 | 필요한 확인 |
|---|---|
| 완료 | 약속한 일이 이루어졌다. 결과를 알릴 사람이 있으면 사람마다 결과가 전달됐다 |
| 철회 | 요청자가 철회했다 |
| 맡지 않음 | 사용자가 맡지 않기로 정했다. 그 결정이 요청자에게 전달됐다 |
| 이관 | 사용자가 넘기기로 정했다. 그 결정이 요청자에게 전달됐다. 넘겨받는 쪽이 인수했다 |
| 요청 아님 | 사용자가 요청이 아니라고 정했다. 미정인 요청에만 쓴다 |

- 확인은 근거 판본으로 채운다. 비서는 근거 판본으로만 채울 수 있다.
- "정했다"는 확인은 사용자만 채운다. 정하기만 하고 나머지 확인이 남았으면 요청은 닫히지 않고 닫힘 예정이 된다. 사유를 적는 것으로는 다른 확인이 채워지지 않는다.
- 사용자는 어느 확인이든 근거 판본 없이 직접 확인해 채울 수 있다. 말로 전했거나 비서가 읽지 못하는 곳에서 이루어진 일을 닫기 위한 것이다. 직접 확인한 것은 어느 확인인지와 함께 사용자 확인으로 닫힘에 남는다. 사용자가 요청을 끝났다고 직접 표시하면 완료의 남은 확인을 직접 확인한 것으로 채워 닫는다.
- 철회의 닫힘 예정은 비서가 철회한 근거를 달아 붙일 수 있다. 맡지 않음과 이관의 닫힘 예정은 사용자만 붙인다.
- 비서는 닫은 뒤의 나중 판본을 근거로 닫힌 요청을 다시 열 수 있다. 사용자가 직접 확인해 채운 확인이 든 닫힘은 다시 열지 못한다. 이때도 판단 모듈이 어긋남을 확인할 사항으로 남긴다. 사용자가 정했다는 확인은 여기에 들지 않는다. 사용자는 언제든 다시 열 수 있다.

## 조회 계약

- **목록** — 열린 요청(또는 닫힌 요청)을 요청의 차례, 작업별 표시, 작업 수와 끝난 수, 보류, 닫힘 예정, 미정, 다음 작업 미정, 풀리지 않은 확인할 사항과 함께 돌려준다. 내 차례인 것만, 닫힘 종류별로 거를 수 있다.
- **목록의 순서** — 사용자가 처리 순서를 정한 요청이 그 순서대로 먼저 오고, 나머지는 긴급도, 중요도, 기한, 접수 시각 순이다. 값이 없는 긴급도와 중요도는 가장 낮은 값 뒤에 온다. 웹 화면과 스킬이 같은 순서를 보도록 원장이 정한다.
- **요청 하나** — 작업, 연결된 기록과 역할, 약속한 결과, 준비 자료, 확인할 사항, 닫힘과 채워진 확인, 변경 이력을 돌려준다. 값마다 정한 주체와 사용자 지정이 걸려 있는지, 걸린 시각, 완료와 닫힘의 확인마다 근거로 채웠는지 사용자가 확인했는지 구분된다. 근거는 판단할 때 본 판본으로 나온다.
- **알릴 일** — 아직 전하지 않은 것과, 전했지만 사용자가 보지 않은 것을 따로 조회할 수 있다.
- **변경 따라가기** — 주어진 순번 뒤의 변경 이력을 돌려준다. 다른 프로세스가 쓴 변경을 화면이 알아채는 데 쓴다.

## 공개 계약

`src/request-ledger/index.ts`가 내보내는 것이다. 인자와 반환 타입의 세부는 구현하면서 이 표에 맞춰 정하고, 표를 바꿔야 하면 스펙을 먼저 고친다.

| 묶음 | 함수 |
|---|---|
| 열기 | `openLedger({ path?, clock?, newId? })` |
| 요청 | `createRequest`, `updateRequest`, `setPriority`, `setOrder`, `mergeRequests`, `splitRequest` |
| 작업 | `addTask`, `updateTask`, `completeTask`, `cancelTask`, `moveTask`, `setContinue` |
| 차례 | `setTurn`, `clearTurn` |
| 기록과 연결 | `addRevision`, `linkRecord`, `moveRecord`, `unlinkRecord` |
| 보류 | `placeHold`, `releaseHold` |
| 닫기 | `setPendingClosure`, `clearPendingClosure`, `closeRequest`, `reopenRequest` |
| 확인할 사항 | `raiseOpenItem`, `resolveOpenItem` |
| 알릴 일 | `addNotice`, `markNoticeDelivered`, `markNoticeSeen`, `listNotices` |
| 준비 자료 | `attachMaterial`, `replaceMaterial` |
| 조회 | `listRequests`, `getRequest`, `changesSince` |

쓰는 함수는 모두 첫 인자로 주체를 받는다. 계약을 어기면 `LedgerError`를 던지고, 오류에는 어떤 규칙을 어겼는지 알 수 있는 코드가 있다.

## 저장 방식

- 파일은 `$AI_BUTLER_HOME/ledger.sqlite`다. 폴더는 `0700`, 파일은 `0600`으로 만든다.
- WAL 모드와 busy timeout을 써서 여러 프로세스가 동시에 읽고 쓸 수 있게 한다. 쓰기는 규칙 검사와 저장을 한 쓰기 트랜잭션 안에서 한다.
- 스키마 버전은 `PRAGMA user_version`으로 관리한다. 열 때 낮은 버전이면 순서대로 올리고, 높은 버전이면 열지 않고 오류를 낸다.

## 완료 조건

S1은 `tests/`의 시나리오 테스트로, 나머지는 `src/request-ledger/`의 테스트로 확인한다.

**사례**

- **S1** VOC 사례를 재현한다. Slack 기록과 Jira 기록을 한 요청에 연결하고 조사, 데이터 변경, 회신 작업을 단다. 결과를 알릴 사람이 있는 요청은 작업이 모두 끝나도 전달 확인 없이는 닫히지 않는다. 사용자가 회신한 기록을 결과 전달 근거로 달아 닫으면, 닫힌 목록에서 요청과 작업, 기록, 채워진 확인을 모두 조회할 수 있다.
- **S31** 사용자가 직접 맡긴 일을 Slack이나 Jira 기록 없이 요청으로 등록한다. 맡기면서 한 말이 접수 원본으로 조회되고, 본문과 출처 `conversation`, 작성자, 말한 시각이 그대로 나온다. 같은 id로 다시 접수해도 기록은 하나다. 제목은 정한 주체가 비서이고 사용자 지정이 없으며, 요청자(사용자)와 맡기면서 명시한 기한은 사용자 지정이 걸려 조회된다. 제목 없이 등록하면 거부된다. 이 기록을 다른 역할로 연결하거나 완료, 닫힘의 확인, 값 변경의 근거로 달면 원본 시각이 아무리 늦어도 거부된다.

**사용자의 지시**

- **S2** 사용자가 긴급도를 정한 뒤 비서가 다른 값을 쓰면 거부되고 값은 그대로다. 사용자 지정을 풀면 값과 정한 주체(사용자)는 그대로이고 사용자 지정만 없는 것으로 조회되며, 그 뒤 비서가 쓰면 반영되고 정한 주체가 비서가 된다. 중요도, 요청자도 같다. 비서가 여러 값을 한 번에 쓸 때 그중 하나가 사용자 지정이 걸린 긴급도이면 쓰기 전체가 거부되어 다른 값과 변경 이력의 순번이 그대로이고, 오류에 긴급도가 나온다.
- **S3** 비서는 보류를 걸 수 없고 처리 순서, 계속하라는 지시, 차례를 쓸 수 없다.
- **S4** 보류된 작업은 비서가 상태를 바꿔도 보류로 조회된다. 비서가 근거 없이 보류를 풀려고 하면 거부된다. 사용자가 풀거나 비서가 재개 조건의 근거를 달아 풀면, 보류 중에 바뀐 상태가 그대로 드러난다.
- **S5** 비서는 근거 없이 작업을 완료로 쓸 수 없다. 사용자가 표시한 완료는 비서가 되돌리거나 다시 시작할 수 없다. 비서가 어긋남을 확인할 사항으로 남기면 요청 조회에 나온다. 조회 결과에서 두 완료가 구분된다.
- **S6** 사용자가 옮긴 기록과 작업을 비서가 옮길 수 없다. 사용자가 정한 연결을 비서가 끊을 수 없고, 사용자가 A에서 끊은 연결을 비서가 `linkRecord`로 A에 다시 만들 수 없다. 사용자가 나눈 두 요청을 비서가 합칠 수 없고, 사용자가 합친 요청을 비서가 나눌 수 없다.

**사실 정정과 판본**

- **S7** 사용자가 작업의 상태를 바로잡은 뒤 비서가 나중 판본을 근거로 쓰면 반영된다. 근거가 없거나 정정보다 먼저인 판본이면 거부된다.
- **S8** 사용자가 약속한 결과를 바로잡은 뒤 비서가 근거 없이 다른 값을 쓰면 거부된다. 나중 판본을 근거로 달면 값이 바뀌고, 정한 주체는 비서이며 사용자 지정은 걸린 채로 조회된다. 그 뒤에 비서가 근거 없이 또 다른 값을 쓰면 거부된다. 사용자 지정을 풀면 비서가 근거 없이 쓸 수 있고, 예전 판본을 근거로 달아도 그 때문에 거부되지 않는다. 기한도 같다.
- **S32** 사용자가 제목을 고친 직후 비서가 제목을 바꾸면 거부된다. 그 뒤 요청에 기록이 연결되거나 작업이 더해지면(직접 더 맡긴 말의 접수 원본, 다른 요청에서 옮겨 온 것 포함) 비서가 근거 없이 제목을 바꿀 수 있고, 정한 주체는 비서이며 사용자 지정은 걸린 채로 조회된다. 시계가 멈춰 시각이 같아도 제목을 쓴 뒤의 쓰기면 센다. 더해진 것 없이 비서가 또 바꾸면 거부된다. 사용자 지정을 풀면 조건 없이 바꿀 수 있다. 사용자 지정이 걸린 A의 제목이 남은 합치기 뒤에는 옮겨 온 작업만으로 비서가 제목을 바꿀 수 있다. B의 사용자 지정 제목을 가져온 합치기 뒤에는 거부되고, 그 뒤 작업이 더해지면 바꿀 수 있다.
- **S9** 정정보다 먼저 만들어진 Jira 티켓이 정정 뒤에 바뀌어 새 판본이 생기면, 그 판본은 나중 판본으로 받아들여진다. 정정 뒤의 판본 둘이 늦은 것부터 도착하면, 앞선 판본을 근거로 한 쓰기는 거부되어 값이 되돌아가지 않는다.
- **S10** 완료 근거로 단 판본은 원본의 새 판본이 들어와도 바뀌지 않고, 요청 조회에서 판단할 때 본 내용으로 나온다. 원본 시각이 같은 판본을 두 번 넣으면 판본은 하나다. 본문이 A, B, 다시 A로 바뀌면 판본은 셋이다.
- **S11** 사용자가 작업의 차례를 정하면 담당과 상태는 그대로이고 조회되는 차례만 바뀐다. 비서가 나중 판본을 근거로 그 작업의 상태를 바꾸거나 작업이 끝나면 사용자가 정한 차례가 풀린다. 보류된 작업은 사용자가 정한 차례가 있어도 차례가 없다.

**차례, 표시, 순서**

- **S12** 한 요청에서 작업 하나가 대기이고 다른 하나가 보류여도, 이들과 무관한 작업은 진행할 수 있음으로 조회되고 요청의 차례에 그 담당이 들어 있다.
- **S13** "조회할 때 계산하는 값" 표의 일곱 줄마다 표시와 차례가 표대로 나온다. 두 줄에 함께 해당하면 위의 줄이 나온다. 닫힘 예정인 요청의 보류된 작업은 멈춰야 함으로, 보류된 요청의 선행 작업 대기인 작업은 보류로, 보류된 대기 작업은 차례 없이 보류로 나온다. 선행 작업이 취소된 작업은 진행할 수 있음으로 나오지 않는다. A가 B를, B가 C를 기다릴 때 C가 A를 기다리게 하는 쓰기는 거부된다.
- **S14** 열린 요청에 끝나지 않은 작업이 없으면 다음 작업 미정으로 조회된다. 닫힘 예정인 요청은 다음 작업 미정으로 나오지 않는다.
- **S15** 미정으로 등록한 요청이 목록에 나오고, 값이 비어 있는 요청자와 약속한 결과를 나중에 채울 수 있다.
- **S16** 목록은 사용자가 정한 처리 순서, 긴급도, 중요도, 기한, 접수 시각 순으로 나온다. 긴급도가 높고 중요도가 낮은 요청이 긴급도가 보통이고 중요도가 높은 요청보다 앞에 온다. 긴급도가 없는 요청은 낮음 뒤에 온다. 사용자가 처리 순서를 정한 요청은 긴급도가 낮아도 맨 앞에 온다.

**닫기**

- **S17** "닫기" 표의 확인을 채우지 못한 닫기는 거부된다. 결과를 알릴 사람이 둘이면 한 사람에게 전달된 근거만으로는 닫히지 않는다. 비서는 "정했다"는 확인을 채울 수 없고, 근거 판본 없이 확인을 채울 수 없다. 사용자가 맡지 않기로 정하고 요청자에게 전달됐다고 직접 확인하면 닫히고, 그 확인이 사용자 확인으로 조회된다. 정하기만 하고 확인하지 않으면 닫히지 않는다. 결과를 알릴 사람이 있는 요청도 사용자가 끝났다고 직접 표시하면 근거 없이 닫히고, 사용자가 표시한 완료로 조회된다.
- **S18** 사용자가 넘기기로 정하기만 하면 요청은 닫히지 않고 닫힘 예정이 된다. 그때 끝나지 않은 작업은 멈춰야 함으로, 닫는 작업과 사용자가 계속하라고 한 작업은 진행할 수 있음으로 조회된다. 요청자 전달은 근거 판본으로, 인수는 사용자 확인으로 채우면 닫힌다.
- **S19** 닫힌 목록에서 완료, 철회, 이관, 맡지 않음, 요청 아님이 구분되고, 사용자가 직접 확인한 것이 어느 확인인지 조회된다. 요청 아님은 미정이 아닌 요청에 쓸 수 없다.
- **S20** 비서가 닫은 요청은 닫은 뒤의 나중 판본으로 다시 열 수 있다. 사용자가 정하고 나머지를 근거 판본으로 채워 닫은 이관도 비서가 다시 열 수 있다. 사용자가 직접 확인한 것이 든 닫힘은 비서가 다시 열 수 없다.

**합치기와 나누기**

- **S21** 합치면 B의 작업, 연결, 보류, 확인할 사항, 준비 자료가 A에서 조회되고 B를 찾으면 A가 나온다. B의 요청 보류는 B에서 온 작업에만 걸린다. A에 사용자 지정이 없고 B에 사용자 지정이 걸린 값은 B에서 넘어오고, 정한 주체와 사용자 지정이 걸린 시각이 B의 것 그대로 조회된다. B에서 10시에 정한 기한을 12시에 합친 뒤 원본 시각이 11시인 판본을 근거로 비서가 기한을 쓰면 반영된다. B에서 이미 11시 30분 판본까지 반영했었다면 합친 뒤의 11시 판본은 거부된다. 양쪽에 사용자 지정이 걸려 있고 값이 다르면 비서의 합치기는 거부되고 사용자의 합치기는 A의 값을 쓴다. A의 기한을 사용자가 정한 뒤 비서가 나중 판본으로 바꿨어도 사용자 지정이 걸린 것으로 본다. B에서 사용자 지정을 푼 값은 넘어오지 않고 합치기를 막지도 않는다.
- **S22** 나누면 고른 작업과 거기 딸린 것만 새 요청으로 가고 A의 요청 단위 값은 남는다. 남는 작업과 선후 관계가 있는 작업만 골라 나누면 거부된다. 닫혔거나 닫힘 예정인 요청은 합치거나 나눌 수 없다. 보류된 요청에서 나누거나 옮긴 작업은 새 요청에서도 보류로 조회되고 재개 조건이 같다. 합치기나 나누기가 중간에 실패하면 아무것도 옮겨지지 않는다.
- **S23** 사용자가 A에서 끊은 기록이 B에 연결돼 있으면 비서는 B를 A에 합칠 수 없다. 사용자가 A에서 나눈 C를 비서가 다른 요청을 거쳐 A와 한 요청에 모을 수 없다. 사용자가 직접 합치면 합쳐지고 그 표시가 지워진다.

**확인할 사항, 알릴 일, 준비 자료**

- **S24** 확인할 사항에 답하면서 값을 바꾸면 둘이 함께 저장되고 변경 이력에 그 답이 근거로 남는다. 값 변경이 거부되면 답도 저장되지 않는다.
- **S25** 알릴 일은 전하지 않은 것, 전했지만 보지 않은 것, 본 것으로 구분해 조회된다.
- **S26** 준비 자료를 바꾸면 요청 조회에 새 내용과 확인한 시각이 나오고, 이전 내용은 변경 이력에 남는다.

**이력과 저장**

- **S27** 모든 쓰기가 변경 이력에 주체, 창구나 모듈, 이전 값과 새 값, 근거, 시각과 함께 남는다. 비서가 정한 값을 사용자가 고치면 비서가 정했던 값과 사용자가 고친 값이 변경 이력 한 건에 함께 남는다. 비서가 정한 값과 같은 값을 사용자가 쓰거나 사용자 지정만 풀어도 한 건이 남는다. 거부된 쓰기와 값, 정한 주체, 사용자 지정이 모두 그대로인 쓰기는 남지 않는다. `changesSince`가 순번 뒤의 변경만 돌려준다.
- **S28** 두 프로세스가 같은 파일에 각각 200번씩 쓰면 400건이 모두 저장되고 변경 이력의 순번에 빠진 것이나 겹친 것이 없다. 한 프로세스가 작업을 보류하는 동안 다른 프로세스가 같은 작업의 상태를 써도 보류가 유지된다.
- **S29** 파일을 닫았다 다시 열어도 데이터가 그대로다. 낮은 스키마 버전의 파일은 데이터를 잃지 않고 올라가고, 높은 버전의 파일은 오류를 낸다.
- **S30** `npm run check`가 통과한다. 이 조건은 명령의 결과로 확인하고 테스트를 따로 두지 않는다.

## 경계

공통 규약의 경계를 따르고 다음을 더한다.

- **항상 한다** — 쓰기 규칙은 SQL이나 호출하는 쪽이 아니라 원장의 쓰기 함수 안에서 검사한다.
- **먼저 묻는다** — "쓰기 계약"과 "닫기" 표의 규칙 변경. 원칙 문서의 판단 기준을 바꾸는 일이므로 원칙 문서도 함께 고친다.
- **하지 않는다** — 다른 모듈이 SQLite 파일을 직접 열어 읽거나 쓰게 하지 않는다. 원장 안에서 모델을 부르거나 채널에 접근하지 않는다.

## 이번 버전에서 하지 않는 것

- 맡긴 범위, AI 팀원, 작업 배정 기록의 저장 — 실행 조율을 시작할 때 별도 스펙으로 더한다.
- 정정을 비슷한 요청에 적용하기 위한 저장 — `corrections` 스펙에서 정한다.
- 사용자의 지시 때문에 거부된 비서의 쓰기를 이력으로 남기는 일 — 거부된 쓰기는 호출한 판단 모듈이 오류로 받는다. 개선에 쓸 형태는 `corrections` 스펙에서 정한다.
- 서로 다른 요청의 작업 사이의 선후 관계 — 같은 요청 안에서만 둔다.
- 긴급도와 중요도를 합친 순위표나 더 잘게 나눈 단계 — 세 단계와 긴급도 우선으로 써 본 뒤에 정한다.
- 본문 검색 — 목록과 요청 조회로 부족해질 때 더한다.
- 오래된 요청, 기록, 판본의 삭제나 보관 정책 — 데이터가 쌓인 뒤에 정한다.
- 파일 암호화와 백업 — 로컬 파일 권한으로 시작한다.
- 첨부 파일과 이미지의 저장 — 판본의 본문과 주소만 저장한다.
