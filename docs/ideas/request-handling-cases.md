# AI Butler의 요청 처리 사례

[AI Butler의 목표](../intent/ai-butler.md)를 실제 요청에 대입해, 사용자가 겪은 일과 비서에게 기대하는 판단을 정리한 문서다.

각 사례의 상태 문구는 표시 예시다. 판단 기준은 목표 문서와 [요청 처리 원칙](../intent/request-handling-principles.md)을 따른다.

사례에는 제품 전체의 모습이 담겨 있다. 비서가 다른 사람에게 직접 회신하는 일, 이메일 같은 새 채널, 연결된 채널에서 요청을 스스로 찾는 일, 자료를 미리 조회해 붙이는 일은 [capability map](../spec/capability-map.md)의 확장 단계에서 다룬다. 첫 버전에서는 회신이 사용자의 작업으로 남고, 사용자가 회신한 기록이 연결된 뒤에 요청을 닫는다.

## 한 대화에서 맡긴 두 가지 일

첫 버전을 점검하려고 만든 시험 상황이다. 실제로 겪은 일이 아니라 첫 버전의 흐름을 한 번에 따라가 보려고 지어냈다.

사용자가 한 대화에서 두 가지 일을 맡긴다. 하나는 CS팀이 Jira 티켓으로 올린 결제 오류의 원인 조사이고, 다른 하나는 주간 지표 리포트 초안 작성이다. 결제 오류는 조사만 맡기고 CS팀 회신은 사용자가 하기로 한다. 리포트는 전부 맡긴다. 사용자가 Jira 티켓을 짚어 주자 비서는 그 티켓을 첫 요청에 연결한다.

비서는 두 요청을 서로 다른 팀원에게 배정한다. 조사를 맡은 팀원이 운영 DB 조회 권한이 필요하다고 묻자, 비서는 승인을 요청하고 목록에 `내 승인 필요 · 운영 DB 조회`를 표시한다. 그동안 리포트를 맡은 팀원은 계속 진행하고 목록에는 `초안 작성 중`이 보인다. 그사이 CS팀이 Jira 티켓에 재현 조건을 덧붙이면 비서는 바뀐 내용을 첫 요청에 반영한다.

사용자가 목록에서 승인하면 조사 팀원만 일을 이어 간다. 리포트 팀원이 초안을 보냈는데 한 지표의 출처가 빠져 있으면, 비서는 부족한 점을 남기고 보완을 맡긴다. 보완된 초안이 오면 근거를 확인해 리포트 요청을 닫고 사용자에게 결과를 알린다.

조사 팀원이 원인과 근거를 보내면 비서는 조사를 완료로 표시하고, `조사 완료 · CS팀 회신은 내 차례`라고 알린다. 요청은 닫히지 않는다. 사용자가 Slack 스레드에 회신하고 그 기록이 연결되면 비서는 전달된 것을 확인해 첫 요청을 닫는다.

이 사례로 사용자가 팀원 세션을 하나씩 열어 보지 않고도 어디까지 진행됐는지, 언제 자신이 나서야 하는지, 무엇이 끝났는지 알 수 있었는지를 점검한다.

## 슬랙으로 받은 POS 에이전트 시크릿 제거 요청

**사용자가 겪은 일.** 요청 하나가 약 20단계로 나뉘었다. 개발 환경 설정 중 일부는 사용자가 먼저 진행할 수 있었고, AWS KMS 키 생성은 SRE 팀이 맡아야 했다. 사용자는 bt-pos와 POS API의 보안을 강화하고 직접 배포했다. 일을 이어갈 때마다 어디까지 끝냈는지, 다른 팀에 무엇을 부탁했고 처리가 끝났는지 다시 파악하는 데 손이 갔다.

**목록에서 보고 싶은 것.** 비서는 개발 환경 설정 중 지금 진행할 수 있는 부분을 보여 준다. KMS 키 생성을 요청한 뒤에는 SRE에 보낸 요청과 확인된 처리 상태를 함께 표시한다. SRE의 조치를 기다리는 동안에도 독립적인 작업은 계속 진행할 수 있다.

**이 사례에서 처음 자동화하고 싶은 일은 배포 기록을 확인해 목록을 갱신하는 것이다.** 사용자가 배포한 뒤 배포 확인을 맡기면, 팀원이 bt-pos와 POS API 각각의 AWS ECS 배포 기록과 WAS 로그를 조회해 근거와 함께 보고하고, 비서가 확인한 서비스의 배포 단계만 완료로 반영한다. 당시 기록을 시간순으로 보면, 한 서비스의 배포만 확인된 시점에도 목록이 두 서비스의 상태를 정확히 구분하는지 점검할 수 있다.

배포 확인을 맡기지 않았다면, 사용자가 연결해 준 기록에 배포 결과가 남았을 때 그 기록으로 반영한다. 다음은 사용자가 두 서비스의 배포를 직접 하고, 비서에게는 배포 확인과 원래 슬랙 스레드에 결과를 회신하는 일까지 맡긴 경우다.

배포 기록과 로그 조회가 이미 허용돼 있고 이 일을 맡을 팀원이 없으면, 비서는 `배포 확인 담당`을 만들어 서비스별 확인 작업을 맡긴다. bt-pos의 배포 기록과 로그가 먼저 돌아오면 bt-pos 단계만 완료로 표시한다. 사용자가 비서에게 “POS API는 내일 확인해”라고 하면 POS API 확인은 보류하고, 다음 날 사용자가 보류를 풀면 같은 팀원에게 그 작업을 이어서 맡긴다. 두 서비스의 배포가 확인되고 원래 요청에서 약속한 일이 회신만 남으면, 비서는 원래 스레드에 결과를 보내고 발송 기록을 확인해 요청을 닫는다. 사용자가 이미 회신했다면 그 기록으로 닫는다. 비서가 직접 회신하는 것은 확장 단계의 일이고, 첫 버전에서는 회신을 사용자의 작업으로 남긴다.

## 시스템에 따라 달라지는 배포와 리뷰

비서가 배포를 맡는 시스템이라면, 제공된 절차에 따라 다른 AI의 리뷰를 거쳐 PR을 만들고 개발 환경에 배포한 뒤 로그와 시스템 상태를 확인할 수 있다. 운영 배포에 승인이 필요하면 기존 승인 시스템에 요청하고 목록에 `운영 승인 대기`를 표시한다. 승인 후에는 운영 배포와 점검을 이어 간다. 사용자가 배포를 시작하는 시스템이라면, 비서는 배포 기록을 확인해 결과를 반영한다. 사용자가 맡긴 범위와 시스템 정보, 실제 진행 상황이 어느 쪽으로 행동할지 결정하는 근거다.

리뷰 담당자도 작업 도중 바뀔 수 있다. 사용자가 PR을 직접 검토하기로 했다면 `내가 할 일 · PR 검토 필요`, 다른 AI가 리뷰하고 있다면 `기다리는 일 · AI 리뷰 중`으로 보인다. 사용자가 의견을 남기면 AI가 수정할 차례이고, 다시 검토할 때가 되면 같은 작업이 사용자 목록으로 돌아온다. 비서가 차례를 잘못 짚었다면 당시 스레드에서 한 약속과 사용자의 정정을 다음 분류에 활용한다.

## 슬랙 보안 감사 요청의 완료 기준

보안 감사 요청에 포함된 POS 시크릿 제거는 앞서 설명한 약 20단계의 POS 에이전트 시크릿 제거와 별개의 작업이다. 이 보안 감사 요청에는 POS 시크릿 제거, bt-pos security-audit 실행, store-trade-backend security-audit 실행이 포함됐다. 세 작업을 모두 마치면 기술 작업은 끝났고 요청자에게 슬랙으로 회신할 일이 남았다는 점이 목록에 드러나야 한다. 표시 예시는 `기술 작업 3/3 완료 · 슬랙 회신 대기`다. 원래 슬랙 요청에 결과를 회신하면 요청 전체를 완료한다.

## 슬랙과 Jira에 걸친 CS팀 VOC 요청

CS팀은 슬랙으로 확인을 요청했고 상세 내용은 Jira 티켓에 있었다. 사용자는 원인을 조사하고 데이터를 변경한 뒤, 원래 슬랙 스레드에 원인과 조치 결과를 답했다. 비서는 슬랙 메시지와 Jira 티켓을 한 요청으로 묶고 사용자의 회신을 완료 기록으로 삼는다. 나중에도 완료 목록에서 문제와 조치 내용을 함께 볼 수 있다.

## 이메일로 받은 고객 결제 취소 요청

비서가 대상 고객과 결제 건을 찾으면 목록에 `내가 할 일 · 관리자에서 결제 취소`를 표시한다. 사용자가 취소를 처리하면 남은 일은 이메일 회신이다. 사용자와 비서 중 누가 회신하든 발송 기록을 확인해 요청을 닫는다.

사용자가 건을 넘겨받을 때마다 결제일과 금액을 다시 조회한다면, 다음에는 조회 단계에서 두 정보를 함께 제시하도록 개선할 수 있다. 회고에서는 어느 정보를 미리 준비하면 재작업이 줄었는지 살핀다. 관리자에서 취소하는 단계는 사용자가 맡기로 한 역할을 따른다.
